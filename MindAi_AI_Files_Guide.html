How the AI Layer Fits Into NestJS

NestJS is the skeleton of the app — it handles HTTP, dependency injection, caching, and sessions. The files inside src/ai/ are the brain — they make LLM calls and process data.

File 1 — model.ts

01 model.ts 59 lines
JOB: Decide which AI model to call for each role

Every AI file needs to know: which LLM do I call? Instead of each file hardcoding a model name, they all call resolveModel(role) from this file.

The 4 roles and their models

// Heavy thinking → big model (70B parameters)
resolveModel('supervisor') → llama-3.3-70b-versatile
resolveModel('chart')      → llama-3.3-70b-versatile

// Simple text → small model (8B parameters, faster & cheaper)
resolveModel('writer')     → llama-3.1-8b-instant
resolveModel('memory')     → llama-3.1-8b-instant

Provider detection

detectProvider(apiKey)
// apiKey starts with "sk-"  →  OpenAI  →  uses gpt-4o-mini
// apiKey starts with other  →  Groq    →  uses llama models

Timeout protection

freshSignal('writer')
// Creates a 15-second timer
// If the LLM takes longer → request is automatically cancelled
// Prevents the app from hanging forever on a slow API
Why it matters: One place to change the model for the entire app. If you want to switch from llama to GPT-4, you change one line here — not 6 different files.

File 2 — skill-prompt.ts

02 skill-prompt.ts 130 lines
JOB: Read AI instructions from Markdown files in the skills/ folder

AI instructions (system prompts) are stored as .md files in skills/ — not inside TypeScript strings. This file provides the tools to read them.

Function 1 — skillFile()

skillFile('chart', 'SKILL.md')
→ "/project-root/skills/chart/SKILL.md"

skillFile('inquiry', 'SKILL.md')
→ "/project-root/skills/inquiry/SKILL.md"

Function 2 — readMarkdownSection()

// Given a SKILL.md with this structure:
// ## Runtime Prompt
// You are a helpful analyst...
// ## Chart Config
// ```json { ... } ```

readMarkdownSection(filePath, 'Runtime Prompt')
→ "You are a helpful analyst..."

// Reads everything under ## Runtime Prompt
// Stops when it hits the next ## heading

Function 3 — readJsonSection()

readJsonSection(filePath, 'Chart Config')
// Finds the ```json block inside that section
// Parses it → returns JavaScript object
// Used to load chart type definitions at startup

Function 4 — interpolateTemplate()

interpolateTemplate("Hello {{USER_NAME}}", { "{{USER_NAME}}": "Alice" })
→ "Hello Alice"

// Used in planner.ts to inject the database schema into the prompt
// at runtime (every request has different data sources)
Why Markdown files? Prompts are hundreds of lines long. Editing them inside TypeScript string literals is painful — no syntax highlighting, no formatting. Markdown files are readable, editable without touching code, and can be versioned separately.

File 3 — planner.ts

03 planner.ts 234 lines
JOB: LLM Call #1 — Turn user question into a MongoDB aggregation pipeline

This is the supervisor — the most critical AI call. It reads the user's question and the database schema, then produces a MongoDB pipeline JSON.

Stage 1 — Build the schema description for the LLM

buildSchemaSection(sources)

// Output example (sent to the LLM as context):
Collection: "projects"  →  query.sourceName = "projects"
  Fields:
    "title"    (string | dimension)
    "budget"   (number | measure)
    "status"   (enum | "completed" | "in_progress" | "planning")
    "category" (enum | "transport" | "health" | "education")

Stage 2 — Call the LLM

generateObject({
  model:    resolveModel('supervisor'),  // llama-3.3-70b
  system:   buildPlannerPrompt(...),       // schema + rules
  messages: [{ role: 'user', content: '{"prompt":"top 5 by budget","intent":"dashboard"}' }],
  schema:   buildPlanSchema(intent),       // forces structured JSON output
})

// LLM returns:
{
  needsData: true,
  query: { sourceName: "projects" },
  pipeline: [
    { "$sort":  { budget: -1 } },
    { "$limit": 5 }
  ],
  strategy:  "overview",
  chartHint: "ranking"
}

Stage 3 — Derive which skills to run next

deriveExecutionSkills(plan, intent)

intent = 'dashboard'  →  ['aggregation', 'chart']
intent = 'report'     →  ['aggregation', 'report']
intent = 'inquiry'    →  ['aggregation', 'inquiry']

// This list tells pipeline.service.ts what to do with the data
Important: The LLM does NOT query MongoDB directly. It only writes the pipeline as a JSON array. NestJS (pipeline.service.ts) executes it. This keeps the database safe — no direct LLM access.

Retry logic (in pipeline.service.ts)

// If MongoDB rejects the pipeline (wrong field name, bad syntax):
hint = "Field validation failed: unknown field 'budjet'. Check casing."

// planner.ts is called again with the hint injected into the prompt
// LLM corrects itself → up to 2 attempts total

File 4 — writer.ts

04 writer.ts 76 lines
JOB: LLM Call #2 for text — Turn data rows into human-readable text

Used for inquiry (direct questions) and report (full analysis). The LLM receives actual data rows and writes text from them.

Function 1 — runInquirySkill()

runInquirySkill({ prompt: "how many projects are completed?", rows: [...] })

// Sends up to 10 rows to the LLM with the question
// Zod schema forces one-field output:

const summarySchema = z.object({
  summary: z.string()    // only one field allowed
})

// LLM returns:
{ summary: "There are 22 completed projects across 6 municipalities." }

Function 2 — runReportSkill()

runReportSkill({ prompt: "analyze transport projects", rows: [...] })

// Zod schema forces structured sections:
const reportSectionsSchema = z.object({
  reportSections: z.array(z.object({
    heading: z.string(),
    body:    z.string()
  })).min(1).max(5)    // 1 to 5 sections
})

// LLM returns:
{
  reportSections: [
    { heading: "Overview",      body: "Transport accounts for 34% of..." },
    { heading: "Key Findings",   body: "North region leads with..." },
    { heading: "Recommendations", body: "Consider reallocating budget..." }
  ]
}
Why generateObject() instead of generateText()? generateText() returns a free string — the frontend can't parse it reliably. generateObject() forces the LLM to return structured JSON that matches the Zod schema. The frontend always gets a predictable shape.

File 5 — memory-skill.ts

05 memory-skill.ts 55 lines
JOB: LLM Call #3 (background) — Extract what to remember from a conversation turn

Runs after the response is already sent to the user. The user never waits for this. It extracts up to 3 structured memory items from each exchange.

How it works

extractMemories(
  prompt:          "show me Qatar infrastructure",
  responseSummary: "Dashboard: Qatar Projects — 22 projects in 6 municipalities"
)

// LLM extracts up to 3 memories:
{
  memories: [
    {
      type:       "context",
      content:    "User is focused on Qatar infrastructure",
      tags:       ["qatar", "infrastructure"],
      importance: 4
    },
    {
      type:       "insight",
      content:    "22 active projects across 6 municipalities in Qatar",
      tags:       ["qatar", "count"],
      importance: 3
    }
  ]
}

The 5 memory types

TypeMeaningExample
goalWhat the user is trying to build"Building a Qatar dashboard"
insightA data finding"22 projects in North region"
preferenceHow the user likes things"Prefers bar charts"
contextBackground about the session"Focused on transport"
decisionA choice the user made"Excluded cancelled projects"

Non-fatal design

try {
  // call LLM, extract memories
} catch (err) {
  log('memory-skill', `extraction failed (non-fatal): ${err}`)
  return []   // never throws — memory failure never breaks the main flow
}

File 6 — embeddings.ts

06 embeddings.ts 60 lines
JOB: Convert text to numbers for semantic search — no API key needed

Uses a local AI model (all-MiniLM-L6-v2, 25MB) that runs in the browser via WASM. No Groq, no OpenAI — completely offline after the first download.

What it produces

generateEmbedding("Qatar infrastructure budget")
→ [0.23, -0.87, 0.45, 0.12, ... 384 numbers total]

// Every text becomes a point in 384-dimensional space
// Similar texts → nearby points → high similarity score

Why this matters — semantic search

// User asks: "Qatar roads"
// Stored memory: "Qatar transport projects"

// Exact text match → would NOT find it (different words)
// Vector similarity → FINDS it (same meaning)

cosineSimilarity(
  embed("Qatar roads"),
  embed("Qatar transport projects")
)
→ 0.91   // very similar — memory is retrieved ✅

Singleton + warmup pattern

// The 25MB model loads only ONCE at server startup
warmupEmbeddings()   // called from main.ts, runs in background

// Prevents two requests loading the model simultaneously:
if (_loading) return _loading   // already loading → wait for it
_loading = loadModel()          // first request triggers the load
Used by: memory.repository.ts — when you ask a question, your prompt is converted to a vector and compared against all stored memories. The most similar ones are injected into the supervisor's context, giving the LLM personalised background knowledge.
