1. Executive Summary

One Sentence Mind Analytics Console turns natural-language questions into charts, reports, and record summaries — backed by real municipal MongoDB data — using a clean pipeline of four AI agents and deterministic code.

The app is built for the Mind Platform, a municipal operations platform used in Qatar. Managers and analysts ask questions in English or Arabic about service requests, inspections, permits, and projects — and instantly see the answer as a dashboard chart, a written Arabic report, or a record summary.

The Central Design Principle Use LLM only where human-level reasoning is required (understanding language, choosing the best visualization). Use deterministic TypeScript code everywhere correctness and safety matter (building database pipelines, rendering charts). This gives us AI intelligence without AI unpredictability in critical paths.

3. Glossary — Key Terms

TaskPlan

The structured JSON the Supervisor Agent produces from the user's natural-language question. It drives every downstream step.

{
  "intent": "dashboard",
  "needsData": true,
  "needsEnrichment": false,
  "needsChart": true,
  "query": {
    "dataStoreName": "ServiceRequests",
    "aggregation": "count",
    "dimensions": ["municipality"],
    "topN": 5,
    "timeRange": { "field": "createdAt", "from": "2024-01-01", "to": "2024-12-31" }
  },
  "chartHint": "ranking"
}

Dataset

The normalized rows returned by the MongoDB runtime after executing the aggregation pipeline.

{
  "rows": [{ "municipality": "Doha", "value": 1200 }, ...],
  "schema": { "municipality": "string", "value": "integer" },
  "source": "mongodb"
}

ChartPlan

The JSON the Chart Planner Agent returns after reading the dataset schema and sample rows.

{
  "chartType": "horizontalBar",
  "xAxisField": "municipality",
  "yAxisField": "value",
  "groupByField": null,
  "title": "أعلى 5 بلديات حسب عدد الطلبات"
}

Permission Scope

The security context sent with every API request. Every MongoDB query is filtered by this scope.

{
  "userId": "u_review",
  "tenantId": "t_mind_qatar",
  "allowedDataStores": ["ServiceRequests", "Inspections", "Permits", "Projects"]
}

Field Role

RoleWhat it isExample
dimensionGroup-by or filter field — categoricalmunicipality, status, serviceType
measureNumeric field for aggregationresponseHours, feeAmount, score
temporalDate/time field for trends and time rangescreatedAt, requestDate

Enrichment

Optional internal knowledge context retrieved by the Search Agent when the Supervisor sets needsEnrichment=true. Used for questions about schemas, data model documentation, or internal platform knowledge. Never fetches external web data.

Conversation Memory

The last 8 turns of conversation stored in MongoDB and included in the planning prompt for follow-up questions. Detects phrases like "same", "also", "نفس", "أيضا" to trigger memory retrieval.

5. Agent Architecture — Who Does What

1. Supervisor Agent LLM

File: src/mastra/agents/supervisor.ts

Job: Convert the user's natural-language prompt into a structured TaskPlan JSON.

Receives: User prompt, available data store schemas, conversation memory

Produces: TaskPlan — dataStoreName, aggregation, dimensions, filters, timeRange, chartHint, needsEnrichment

Why LLM: Natural language → structured data. Only an LLM can understand "top 5 municipalities by complaints last month" and extract dataStore=ServiceRequests, topN=5, aggregation=count, dimension=municipality, timeRange=last 30 days.

2. MongoDB Runtime Deterministic Code

File: src/mastra/runtime/mongodb-runtime.ts

Job: Build and execute the MongoDB aggregation pipeline safely.

Receives: TaskPlan + PermissionScope

Produces: Dataset — { rows, schema, jsonSchema }

Why NOT LLM: The TaskPlan is already fully structured — no reasoning needed. Deterministic code is faster, safer, and enforces tenant scope perfectly. An LLM adding another layer here would only add latency and risk.

Tools called directly (no LLM): buildAggregationFromPlan() → executePipeline() → validateRows()

3. Chart Planner Agent LLM

File: src/mastra/agents/chart.ts

Job: Read the actual MongoDB pipeline output and decide the best visualization.

Receives: datasetSchema, 3 sample rows, rowCount, supervisorHints, userPrompt, candidateTypes

Produces: ChartPlan — chartType, xAxisField, yAxisField, groupByField, title (Arabic)

Why LLM: The agent reads the real data shape (not just the user's words) and makes a visualization decision. It can distinguish "two string fields + one numeric = clustered bar" from "one string field + one numeric = simple bar/donut" — something that requires reasoning about data structure.

Always runs for non-empty datasets. Sole decision maker — no deterministic bypass.

4. Search Agent LLM

File: src/mastra/agents/search.ts

Job: Search the internal knowledge corpus when the Supervisor sets needsEnrichment=true.

Receives: topic, tenantId, dimensions, optional timeRange

Produces: Context rows + citations from internal knowledge

Tool: vectorSearch — semantic search over exported DB JSON

Why LLM: Semantic understanding required to find relevant knowledge chunks and format them as structured rows.

5. Writer Agent LLM

File: src/mastra/agents/writer.ts

Job: Convert data rows into readable Arabic narrative — for reports and inquiry summaries.

Receives: dataset rows, enrichment context, user prompt

Produces: reportSections (heading + body) or summary string

Why LLM: Natural language generation. Only an LLM can convert numbers into meaningful Arabic narrative.

MongoDB Agent Removed — Not Used

File: src/mastra/agents/mongodb.ts (kept as reference, not registered)

Defined as an LLM agent that could orchestrate buildAggregation + executePipeline + validateRows tools. Removed from Mastra registration because the MongoDB Runtime (deterministic code) does this job better — faster, safer, and without LLM overhead. The TaskPlan from the Supervisor is already fully structured; there is nothing left for an LLM to reason about.

7. Request Lifecycle — Step by Step

Dashboard Request Example

User asks: "top 5 municipalities by service request count this month"

Step 1 — Supervisor Agent (LLM)

Input:  prompt + ServiceRequests schema + conversation history
Output: {
  "intent": "dashboard",
  "needsData": true,
  "needsChart": true,
  "needsEnrichment": false,
  "query": {
    "dataStoreName": "ServiceRequests",
    "aggregation": "count",
    "dimensions": ["municipality"],
    "topN": 5,
    "timeRange": { "field": "createdAt", "from": "2024-05-01", "to": "2024-05-29" }
  },
  "chartHint": "ranking"
}

Step 2 — finalizeTaskPlan() — pure code

Validates and normalizes field names against the real DataStore schema.
Infers time ranges from relative phrases ("this month" → ISO dates).
Ensures dimensions exist in the schema.
Output: same TaskPlan with corrected field names + absolute dates.

Step 3 — MongoDB Runtime — pure code

buildAggregationFromPlan() produces:
[
  { "$match": { "tenantId": "t_mind_qatar",
                "createdAt": { "$gte": ISODate("2024-05-01"), "$lte": ISODate("2024-05-29") } } },
  { "$group": { "_id": { "municipality": "$municipality" },
                "value": { "$sum": 1 } } },
  { "$project": { "municipality": "$_id.municipality", "value": 1, "_id": 0 } },
  { "$sort": { "value": -1 } },
  { "$limit": 5 }
]

executePipeline() runs this against MongoDB.
validateRows() types every field.

Dataset returned:
{
  "rows": [
    { "municipality": "Doha",    "value": 1420 },
    { "municipality": "Al Wakra","value": 980  },
    { "municipality": "Al Khor", "value": 740  },
    { "municipality": "Lusail",  "value": 620  },
    { "municipality": "Al Rayyan","value": 510 }
  ],
  "schema": { "municipality": "string", "value": "integer" },
  "source": "mongodb"
}

Step 4 — Chart Planner Agent (LLM)

Input sent to the agent:
{
  "datasetSchema": { "municipality": "string", "value": "integer" },
  "sampleRows": [
    { "municipality": "Doha",    "value": 1420 },
    { "municipality": "Al Wakra","value": 980  },
    { "municipality": "Al Khor", "value": 740  }
  ],
  "rowCount": 5,
  "supervisorHints": {
    "intentHint": "ranking",
    "suggestedXAxis": "municipality",
    "suggestedYAxis": null,
    "suggestedGroupBy": null
  },
  "userPrompt": "top 5 municipalities by service request count this month",
  "candidateTypes": ["bar", "horizontalBar", "donut"]
}

Agent reads: intentHint=ranking → horizontalBar, string field → xAxis, numeric → yAxis

Output:
{
  "chartType": "horizontalBar",
  "xAxisField": "municipality",
  "yAxisField": "value",
  "title": "أعلى 5 بلديات حسب عدد الطلبات"
}

Step 5 — validateChartPlan() — pure code

Checks that chartType is in candidateTypes ✓
Checks that xAxisField "municipality" exists in schema ✓
Checks that yAxisField "value" exists in schema ✓
Throws if any check fails — no silent fallback.

Step 6 — chart-tools.ts — pure code

buildChartFromDataset() receives full rows + validated ChartPlan.
Returns complete ECharts option:
{
  "chartType": "horizontalBar",
  "option": {
    "title": { "text": "أعلى 5 بلديات حسب عدد الطلبات" },
    "xAxis": { "type": "value" },
    "yAxis": { "type": "category", "data": ["Doha","Al Wakra","Al Khor","Lusail","Al Rayyan"] },
    "series": [{ "type": "bar", "data": [1420,980,740,620,510] }],
    "tooltip": { "trigger": "axis" }
  },
  "accessibility": { "description": "مخطط أعمدة أفقي..." }
}

Total time: ~3-5 seconds. LLM calls: 2 (Supervisor + Chart Planner).

File: src/mastra/agents/supervisor.ts   Runtime: src/mastra/runtime/supervisor-runtime.ts

What It Decides

FieldWhat it meansExample
dataStoreNameWhich MongoDB collection to queryServiceRequests
aggregationHow to aggregate: count / sum / avg / min / maxcount
dimensionsGroup-by fields["municipality"]
filtersWHERE conditions[{field:"status",op:"eq",value:"new"}]
timeRangeDate window{field:"createdAt",from:"...",to:"..."}
topNLimit + sort by value DESC5
chartHintSuggested chart type for chart agentranking

What It Does NOT Do

  • Does not write MongoDB queries — that is the runtime's job
  • Does not pick xAxisField / yAxisField — that is the chart agent's job
  • Does not write report text — that is the writer agent's job

finalizeTaskPlan() — post-processing

After the supervisor returns its plan, src/mastra/task-plan.ts runs a set of deterministic corrections:

  • Validates field names against the real DataStore schema
  • Converts relative time ranges ("last 30 days") to absolute ISO dates
  • Infers dimensions from prompt patterns ("by X" → dimensions=["X"])
  • Infers filters from Arabic status terms (قيد المراجعة → under_review)
  • Forces a temporal dimension for trend charts

9. MongoDB Runtime — Data Layer

File: src/mastra/runtime/mongodb-runtime.ts

Important This is NOT an LLM. It is pure TypeScript code. The mongodbAgent LLM definition exists in the codebase as a reference but is not registered or called by any workflow.

The Three Functions It Calls

FunctionFileWhat it does
buildAggregationFromPlan()src/analytics/builders/build-pipeline.tsConverts TaskPlan → MongoDB aggregation pipeline stages
executePipeline()src/mastra/tools/mongodb-tools.tsRuns the pipeline against MongoDB with tenant scope
validateRows()src/mastra/tools/mongodb-tools.tsTypes every field, removes _id, returns clean dataset

Pipeline Builders

Builder fileMongoDB stage
build-match-stage.ts$match — tenant filter + user filters + time range
build-group-stage.ts$group — aggregation by dimensions
build-project-stage.ts$project — rename _id fields, expose value
build-sort-stage.ts$sort — sort by value DESC for rankings
build-limit-stage.ts$limit — topN support
build-having-stage.ts$match (post-group) — filter by aggregate value
build-lookup-stage.ts$lookup — joins between collections

Two Query Functions

runMongoDatasetQuery() — used by dashboard and report. Runs full aggregation with GROUP BY, COUNT/SUM/AVG, topN, etc.

runMongoRecordFetch() — used by general-question inquiry. Fetches individual records without aggregation. Returns raw rows for record links.

10. Chart Planner Agent — Visualization Intelligence

File: src/mastra/agents/chart.ts   Runtime: src/mastra/runtime/chart-runtime.ts

What It Receives

{
  "datasetSchema":   { "municipality": "string", "value": "integer" },
  "sampleRows":      [ up to 3 real rows from MongoDB pipeline ],
  "rowCount":        22,
  "supervisorHints": {
    "intentHint":      "ranking",
    "suggestedXAxis":  "municipality",
    "suggestedYAxis":  null,
    "suggestedGroupBy": null
  },
  "userPrompt":      "top 5 municipalities by service requests",
  "candidateTypes":  ["bar", "horizontalBar", "donut"]
}

What It Returns

{
  "chartType":    "horizontalBar",
  "xAxisField":   "municipality",
  "yAxisField":   "value",
  "groupByField": null,
  "title":        "أعلى البلديات حسب عدد الطلبات"
}

How It Makes Decisions

The agent follows a two-step process:

Step 1: If supervisorHints.intentHint is present, follow it (trend→line, ranking→horizontalBar, etc.)

Step 2: If no intentHint, read the datasetSchema and infer from the data shape. See Section 11 for the complete shape → chart map.

validateChartPlan() — strict validation

After the agent responds, validateChartPlan() checks:

  • chartType is in candidateTypes — throws if not
  • xAxisField exists in the dataset schema — throws if not
  • yAxisField exists in the dataset schema — throws if not
  • groupByField (if set) exists in the dataset schema — throws if not

There is no silent fallback. If the agent returns invalid fields, the request fails with a clear error. This keeps the system honest — chart quality is owned entirely by the agent.

After Validation — chart-tools.ts

The validated ChartPlan plus the full rows dataset are passed to buildChartFromDataset() in src/mastra/tools/chart-tools.ts. This function builds the complete ECharts option object deterministically. The LLM never touches ECharts configuration.

11. Data Shape → Chart Type (Complete Map)

Core idea The MongoDB pipeline always returns a predictable data shape. The chart agent reads that shape from datasetSchema and sampleRows and maps it to the correct chart configuration — including whether to set groupByField for clustered charts.
#Data Shape (datasetSchema)Example SchemaChart TypegroupByField
1 temporal + numeric { createdAt: "date", value: "integer" } line none
2 temporal + string + numeric
(multi-series time)		 { createdAt: "date", municipality: "string", value: "integer" } line string field → one line per value
3 string + numeric, rowCount ≤ 12 { status: "string", value: "integer" } donut none
4 string + numeric, rowCount > 12 { municipality: "string", value: "integer" } horizontalBar none
5 string + string + numeric
(grouped / clustered)		 { municipality: "string", status: "string", value: "integer" } bar (clustered) secondary string field (e.g. status)
6 two or more numerics, no temporal { responseTime: "number", resolutionRate: "number" } scatter string field if present
7 geo + numeric { region: "geo", value: "integer" } map none
8 single numeric, rowCount > 20
(distribution)		 { responseTime: "number" } histogram none

Shape 5 — Clustered Bar — Key Case

This is the most important shape to understand. When the MongoDB pipeline groups by two dimensions (e.g. municipality AND status), the output has two string fields plus a value. The chart agent sets groupByField to the secondary string field, which tells chart-tools.ts to render a clustered bar chart where each bar group is one municipality and each bar color is one status.

MongoDB query:   count by municipality AND status
Dataset:         { municipality: "string", status: "string", value: "integer" }
ChartPlan:       {
                   chartType: "bar",
                   xAxisField: "municipality",
                   yAxisField: "value",
                   groupByField: "status"    ← makes it clustered
                 }
ECharts result:  Grouped bar — one cluster per municipality,
                 one bar per status (new / in_review / completed...)

12. Writer Agent

File: src/mastra/agents/writer.ts   Runtime: src/mastra/runtime/writer-runtime.ts

The Writer Agent converts data rows into Arabic narrative text. It is used by both the Report and Inquiry workflows.

For Reports

Receives the aggregated dataset + optional enrichment context + user prompt. Returns an array of sections, each with a heading and body in Arabic. Each section covers one analytical angle (overview, by-dimension breakdown, time trend, conclusions).

For Inquiries

Receives raw records + user prompt. Returns a single Arabic summary paragraph plus the app extracts up to 10 record links (id + label) for direct navigation.

13. Search Agent

File: src/mastra/agents/search.ts   Runtime: src/mastra/runtime/search-runtime.ts

Triggered only when the Supervisor sets needsEnrichment=true. This happens when the user explicitly asks about internal knowledge — collection schemas, data model documentation, or platform metadata — not for external benchmarks or public data.

How It Works

  • Has one tool: vectorSearch — semantic search over exported DB JSON indexed in MongoDB
  • Falls back to lexical search if semantic indexing is unavailable
  • Returns rows formatted to match the primary dataset's dimension fields (for merging)
  • Returns citations — title + snippet for each knowledge chunk used

When to Use

needsEnrichment=true:   "what fields does the ServiceRequests collection have?"
                         "explain the data model for inspections"
                         "show me the schema for permits"

needsEnrichment=false:   "top 5 municipalities by complaints"  ← just data, no knowledge needed
                         "national benchmarks for response time" ← external, not internal

16. Security & Tenant Safety

Read-only The app can never modify, insert, or delete data. Every query uses MongoDB aggregation pipelines — no update, insertOne, or deleteMany ever runs.

Tenant Isolation

Every MongoDB query starts with a $match stage that filters by tenantId from the PermissionScope. The LLM never sees or sets the tenantId — it is injected by the runtime from the authenticated request scope.

DataStore Allowlist

The Supervisor can only reference data stores in scope.allowedDataStores. The runtime rejects any query targeting a collection not in this list.

LLM Never Writes Queries

The Supervisor outputs a structured TaskPlan JSON. TypeScript builders in src/analytics/builders/ convert it to a MongoDB pipeline. The LLM never produces raw $match, $group, or any MongoDB operator syntax.

Field Validation

finalizeTaskPlan() validates every field name in the plan against the real DataStore schema before any query runs. Unknown fields are removed. This prevents the LLM from querying fields that don't exist.

Chart Field Validation

validateChartPlan() checks that every field name returned by the Chart Planner Agent exists in the real dataset schema. An invalid field name throws immediately — the chart never renders with invented field names.

20. Team Presentation Script

Opening — 2 minutes "Mind Analytics Console answers questions about municipal data in plain English or Arabic. You type a question, you get a chart, a report, or a record list — instantly, with no database knowledge required."

Slide 1 — The Three Modes

Show the three endpoints. Ask: "who in this room has written a MongoDB query before?" Then: "this app does that for you."

Slide 2 — The Agent Architecture

Draw the pipeline on a whiteboard or show Section 4's diagram:

User prompt
→ Supervisor Agent (LLM)     understands the question
→ MongoDB Runtime (code)     fetches the data safely
→ Chart Planner Agent (LLM)  picks the best visualization
→ chart-tools (code)         builds the ECharts config
→ chart in browser

Key message: "The AI plans, TypeScript executes."

Slide 3 — Why LLM for Chart Planning?

Show Shape 5 from Section 11. Say: "When MongoDB returns data with two categorical fields and one numeric, the chart agent recognizes this as a clustered bar chart and sets groupByField automatically. No hardcoded rule covers every case — that's why we use an LLM."

Slide 4 — Why NOT LLM for MongoDB?

"The Supervisor already turned the question into a structured plan. By that point, there's nothing left to reason about — just execute. Code is faster, safer, and 100% predictable. An LLM adding another layer would just add 10 seconds of latency and potential errors."

Slide 5 — What Changed in v3

Show the bug fix table from Section 18. Highlight: chart agent now always runs, grouped data produces clustered charts, 12 bugs fixed.

Demo Flow — Recommended Sequence

1. "service request count by municipality"
   → shows simple bar/horizontalBar chart

2. "service request count by municipality and status"
   → shows CLUSTERED bar chart  (Shape 5 — the new feature)

3. "daily service request count over the last 30 days"
   → shows LINE chart with temporal x-axis

4. "top 5 municipalities by service requests"
   → shows HORIZONTAL BAR chart (ranking intent)

5. "analyze service request volume by municipality over last 90 days"
   → shows REPORT with Arabic sections + chart
Common Question: Why not let the LLM write the MongoDB query directly? Security. An LLM could write a query that accesses another tenant's data, drops a collection, or returns millions of records. By converting the user's request to a structured TaskPlan first, and then converting that plan to a pipeline in TypeScript code, we guarantee that tenantId filtering always happens, only allowed fields are queried, and read-only aggregation stages are the only thing that runs.
Closing message "This app shows the right way to build AI analytics: use LLM intelligence for language and judgment, use deterministic code for data access and rendering. Each component does one job. The result is a system that's powerful, safe, and easy to reason about."
