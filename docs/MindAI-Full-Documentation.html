1. Executive Summary

One Sentence Mind Analytics Console is an AI-powered analytics service that turns natural-language questions into charts, reports, and search results — backed by real municipal MongoDB data, with no SQL knowledge required.

The app is built for the Mind Platform — a municipal operations platform used in Qatar. It gives managers and analysts a way to ask questions about service requests, inspections, permits, and projects, and instantly see the answer as a dashboard chart, a written Arabic report, or a list of matching records.

The most important design choice: the AI plans, but TypeScript code executes the database query safely. The LLM never writes raw MongoDB code. It creates a structured JSON plan, and deterministic builders convert that plan into a validated, tenant-scoped aggregation pipeline.

Tech stack: Express (server) · MongoDB (data) · Mastra (AI workflow framework) · OpenRouter or Groq (LLM provider) · ECharts (charts in browser).

What Data It Works With

The app answers questions about four municipal collections:

  • Service Requests — citizen requests (status, municipality, type, priority, channel, response time)
  • Inspections — field compliance assessments (outcome, inspector team, score)
  • Permits — building/construction permit applications (type, status, processing days, fees)
  • Projects — municipal projects (stage, contractor, budget, completion %)

Why It Is Useful

  • No SQL or database knowledge needed — ask in plain English or Arabic
  • Prompt suggestions auto-generated from real data (not hardcoded examples)
  • Full audit trail — see exactly what the AI planned and what MongoDB pipeline ran
  • Conversation memory — follow-up questions work naturally
  • Tenant-safe — every query is scoped to the correct organization
  • Read-only — can never modify platform data

3. Glossary — Key Terms Defined

Data Store

A logical dataset in the platform. It maps one-to-one with a MongoDB collection. The app learns about available data through data store metadata stored in the data_stores collection.

{
  "name": "ServiceRequests",
  "collection": "service_requests",
  "description": "Citizen service requests",
  "fields": [ ... ]
}

Field

A property inside a data store (e.g. municipality, status, createdAt, responseHours). Each field has a type and a role.

Field Type

TypeMeaning
stringText value
numberDecimal number
integerWhole number
booleanTrue / false
date / datetimeDate or timestamp
enumString with a fixed set of allowed values
referenceForeign key to another collection
geoGeographic coordinates
textLong searchable text

Field Role

RoleMeaningExample
idIdentifier — never used as dimension or metric_id, tenantId
dimensionGroup-by or filter fieldmunicipality, status
measureNumeric field for aggregationresponseHours, feeAmount
temporalDate/time field for time ranges and trendscreatedAt

TaskPlan

The structured JSON object created by the Supervisor Agent from the user's natural-language question. It tells the query engine exactly what to do.

{
  "intent": "dashboard",
  "needsData": true,
  "needsEnrichment": false,
  "needsChart": true,
  "query": {
    "dataStoreName": "ServiceRequests",
    "aggregation": "count",
    "dimensions": ["municipality"],
    "topN": 5
  },
  "chartHint": "ranking"
}

Dataset

The normalized rows returned from MongoDB or the search agent. Always has rows, schema, and source.

{
  "rows": [{ "municipality": "Doha", "value": 1200 }, ...],
  "schema": { "municipality": "string", "value": "number" },
  "source": "mongodb"
}

Permission Scope

The security context sent with every API request. Enforced server-side on every database query.

{
  "userId": "u_review",
  "tenantId": "t_mind_qatar",
  "allowedDataStores": ["ServiceRequests", "Inspections", "Permits", "Projects"]
}

Audit

Extra execution details returned by every API response. Contains the TaskPlan, MongoDB pipeline, field schema, enrichment data, and elapsed time. Shown in the UI audit panel.

Enrichment

Optional internal context retrieved by the Search Agent. Only triggered when the Supervisor sets needsEnrichment=true — for example when the user asks about schemas, data model documentation, or internal platform knowledge. Never used for external web data.

Conversation Memory

The last 8 turns of conversation stored in MongoDB and included in the planning prompt for follow-up questions. Example: if the user says "show the same but for last year", the app uses conversation memory to understand what "the same" refers to.

Key Architectural Decisions

AI Plans, TypeScript Executes The LLM never writes raw MongoDB queries. It produces a structured TaskPlan JSON. TypeScript builders in src/analytics/builders/ convert that plan to a safe pipeline. This is the central safety guarantee of the app.
Metadata-Driven The app has no hardcoded business logic per collection. Add a new data store with correct field metadata and the planner and query engine can use it automatically.
Tenant Guard Is Always Enforced Every MongoDB aggregation is guaranteed to start with { $match: { tenantId: "..." } }. Even if a bug in the builder omits it, the executor prepends it automatically.

Dynamic Prompt Suggestions

On page load, the UI calls GET /api/meta. The backend:

  1. Reads actual data stores from MongoDB
  2. Generates deterministic suggestions based on field metadata
  3. Tries to polish them with the Writer Agent (Arabic labels, better phrasing)
  4. Falls back to deterministic suggestions if the LLM times out

This means the suggestion buttons always reflect the actual data — not hardcoded examples.

After every request, the collapsible audit panel shows:

  • Conversation Thread ID — for follow-up tracking
  • Intent — dashboard / report / inquiry
  • Duration — elapsed milliseconds
  • Search Agent Impact — whether enrichment was used and what effect it had
  • TaskPlan — the exact JSON plan the Supervisor created

Tip for demos The audit panel is your best tool for explaining the app to technical stakeholders. Show the TaskPlan and MongoDB pipeline to demonstrate that the LLM does not run arbitrary database code.

7. Request Lifecycle — Step by Step

Outer Pattern (All POST Endpoints)

1.  Express receives HTTP POST request
2.  Zod validates request body (contracts.ts)
3.  API creates unique run ID (logged in x-run-id header)
4.  AnalyticsService resolves conversation reference (threadId / resourceId)
5.  AnalyticsService checks if prompt is a follow-up question
6.  If follow-up → loads last 8 conversation turns from MongoDB
7.  Builds enriched planning prompt with conversation context
8.  Starts matching Mastra workflow with timeout (WORKFLOW_TIMEOUT_MS)
9.  Workflow returns result
10. AnalyticsService saves user + assistant turns to conversation_memory
11. Zod validates response shape
12. API sends JSON response with x-run-id header

Follow-Up Detection

A prompt is detected as a follow-up if it matches any of these patterns:

English: same, again, also, too, previous, above, that, those, it, them, compare it, what about
         use/keep/with the same
Arabic:  نفس، أيضا، السابق، أعلاه، هذا، هذه، ذلك، تلك، قارنها، ماذا عن

Dashboard Workflow Lifecycle

POST /api/dashboard
  └── analyticsService.runDashboard()
        └── dashboardWorkflow (Mastra)
              │
              ├── Step 1: PLAN
              │     supervisorAgent.generate(prompt + dataStores + conversationMemory)
              │     → parse TaskPlan JSON
              │     → finalizeTaskPlan() repairs/normalizes fields
              │
              ├── Step 2a: QUERY (parallel with 2b)
              │     buildAggregationFromPlan(plan, dataStore, scope)
              │     → runAggregation(pipeline, collection, scope)
              │     → validateRows(rows, dataStore)
              │     → returns Dataset { rows, schema, jsonSchema }
              │
              ├── Step 2b: ENRICH (parallel with 2a, only if needsEnrichment=true)
              │     searchAgent.generate(enrichment task)
              │     → vectorSearch tool
              │     → returns Dataset { rows, schema, citations }
              │
              ├── Step 3: MERGE
              │     if enrichment exists → mergeDatasets(primary, secondary, joinKey)
              │
              └── Step 4: CHART
                    chartPlannerAgent.generate(schema + tiny sample + Supervisor hints)
                    → sanitize chart plan
                    → buildChartFromDataset(dataset, plan)
                    → returns ECharts option object

Report Workflow Lifecycle

POST /api/report
  └── reportWorkflow
        ├── Plan → Query + Enrich (parallel) → Merge
        └── Parallel:
              ├── writerAgent.generate(dataset + prompt)  → reportSections[]
              └── chartPlannerAgent.generate() (if needsChart=true) → chart

Inquiry Workflow Lifecycle

POST /api/inquiry
  └── generalQuestionWorkflow
        ├── Plan → fetch MongoDB records (no aggregation, raw documents)
        ├── Optional context retrieval (parallel)
        └── writerAgent.generate(records + prompt)  → { summary, recordLinks }

Conversation Memory Lifecycle

MongoDB collection: conversation_memory

On every request:
  1. Resolve threadId + resourceId (from request or generate fallback)
  2. Load last 8 turns (4 exchanges) from MongoDB
  3. Format as:
     "Recent conversation memory, oldest to newest:
      [dashboard:user] top 5 municipalities ...
      [dashboard:assistant] Dashboard generated for ServiceRequests by municipality...
      Current dashboard request:
      show the same for last year"
  4. Pass this enriched prompt to the Supervisor Agent

After workflow completes:
  5. Save user turn: { threadId, resourceId, tenantId, userId, role:"user", content, createdAt }
  6. Save assistant turn: { ..., role:"assistant", content: summary/description }

8. AI Agents & Workflows

Supervisor Agent

src/mastra/agents/supervisor.ts

Job: Convert a natural-language question into a structured TaskPlan JSON. It is the brain that decides what to query, how to query it, and what kind of output to produce.

Rules enforced in its prompt:

  • Dashboard: needsData=true, needsChart=true
  • Report: needsData=true, chart only if user explicitly asks
  • Inquiry: needsData=true, needsChart=false
  • "top N" → sets topN=N and chartHint="ranking"
  • Counts: aggregation="count", no metric field
  • Sums: aggregation="sum" with a measure field
  • Averages: aggregation="avg" with a measure field
  • Never uses _id or tenantId as dimensions
  • Enrichment only for explicit internal knowledge / schema / documentation requests
  • Time range must be an object { field, from, to } — never a string like "last 30 days"

Output example:

{
  "intent": "dashboard",
  "needsData": true,
  "needsEnrichment": false,
  "needsChart": true,
  "query": {
    "dataStoreName": "ServiceRequests",
    "aggregation": "count",
    "dimensions": ["municipality"],
    "filters": [{ "field": "status", "op": "eq", "value": "new" }],
    "topN": 5
  },
  "chartHint": "ranking"
}

Task Plan Finalizer

src/mastra/task-plan.ts

After the Supervisor returns a plan, finalizeTaskPlan() repairs and normalizes it. This is critical — the LLM may use slightly wrong field names or miss dimensions implied by the prompt.

What it does:

  • Normalizes data store name to match exact MongoDB name
  • Removes field names that don't exist in the data store metadata
  • Infers dimensions from prompt phrases like "by municipality" → ["municipality"]
  • Infers filters from phrases like "open permits" → [{field:"status", op:"in", value:["submitted","under_review"]}]
  • Infers "urgent" → [{field:"priority", op:"eq", value:"urgent"}]
  • Infers "violations" → [{field:"outcome", op:"eq", value:"violation"}]
  • Infers "completed projects" → [{field:"stage", op:"eq", value:"completed"}]
  • Infers relative time ranges: today, yesterday, last N days, this month, this year, recent (=30 days)
  • Infers topN from phrases like "top 5", "أعلى 10"
  • Infers percentOf when user asks for "percentage/share/نسبة"
  • Auto-adds temporal dimension for trend charts (line charts need a date field)
  • Clears metric field when aggregation is "count"
  • Forces intent to match the endpoint called

Dimension inference patterns (English + Arabic):

"by municipality" / "حسب البلدية"  →  municipality
"by zone"         / "حسب المنطقة"   →  zone
"by status"       / "حسب الحالة"    →  status
"by permit type"  / "حسب نوع التصريح" →  permitType
"by contractor"   / "حسب المقاول"   →  contractor
... (20+ patterns total)

MongoDB Agent

src/mastra/agents/mongodb.ts

Defines the data-layer contract with tools: resolveDataStore, buildAggregation, executePipeline, validateRows. In normal workflow execution, the runtime uses deterministic TypeScript builders directly — not the LLM — for database safety.

Writer Agent

src/mastra/agents/writer.ts

Job: Write Arabic text for inquiry summaries and report sections. Grounds every sentence in the provided dataset — never invents figures.

Rules:

  • Always writes in Arabic
  • Inquiry summaries: 2–4 sentences, lead with most notable finding
  • Reports: concise analyst brief — what happened → where concentrated → notable comparisons
  • Uses human-readable field labels: "رسوم التصاريح" not "permitFee"
  • Uses percent field when present: "تمثل بلدية X نسبة 34% من الإجمالي"
  • Returns JSON only — no markdown, no prose outside the JSON
  • If dataset is empty: says clearly that no data was found

Chart Planner Agent

src/mastra/agents/chart.ts

Job: Decide how to visualize the data. Receives the schema, up to 3 sample rows, row count, the user prompt, and Supervisor hints (never the full dataset). Returns a chart plan that the deterministic ECharts builder then renders.

Field selection rules:

  • xAxisField priority: temporal field → geo field → string/boolean dimension
  • yAxisField priority: fields named value/count/total/sum/avg/rate → any other numeric
  • clusters: optional string field for grouped/clustered series
  • Excluded: _id, tenantId, fields ending in "Id", fields starting with "__"

Chart type selection by intentHint:

Internal Search Agent

src/mastra/agents/search.ts

Job: Search the platform's internal knowledge corpus when the Supervisor requests enrichment. Uses vectorSearch tool. If embeddings are indexed, uses semantic search. Otherwise falls back to lexical search over samples/db-export/ JSON files.

Hard rules:

  • Never uses web search, web fetch, scraping, or public benchmarks
  • Never invents facts outside the internal search results
  • Returns empty rows and citations if vectorSearch finds nothing
  • Only activated when needsEnrichment=true in the TaskPlan

10. MongoDB Query Engine

Core Principle The LLM creates a TaskPlan. TypeScript code in src/analytics/builders/ converts that plan to a MongoDB aggregation pipeline. The executor enforces safety rules. The LLM never writes database code directly.

Pipeline Build Order

File: src/analytics/builders/build-pipeline.ts

1.  $match           ← tenant guard + filters + time range
2.  $lookup / $unwind ← joins to other collections (if defined in metadata)
3.  $group            ← count / sum / avg / min / max by dimensions
4.  having $match     ← filter after grouping (like SQL HAVING)
5.  $project          ← rename _id fields to readable names, keep only needed fields
6.  percent stages    ← calculate percentage share if percentOf requested
7.  $sort             ← value descending (for topN) or explicit sort
8.  $limit            ← topN or default 1000 (max 5000)

$match Stage

File: src/analytics/builders/build-match-stage.ts

Always starts with { tenantId: scope.tenantId }. Also adds:

  • scope.rowFilter — extra filters from the API caller
  • TaskPlan filters (status, priority, outcome, etc.)
  • Time range filters using $gte / $lte on the temporal field

Supported filter operators:

OperatorMongoDB Equivalent
eq{ field: value }
ne{ field: { $ne: value } }
gt / gte{ field: { $gt/$gte: value } }
lt / lte{ field: { $lt/$lte: value } }
in{ field: { $in: [values] } }
nin{ field: { $nin: [values] } }
regex{ field: { $regex: value, $options: "i" } }

$group Stage

File: src/analytics/builders/build-group-stage.ts

  • Temporal dimensions are formatted as %Y-%m-%d using $dateToString
  • count → { "$sum": 1 }
  • sum, avg, min, max → use the selected metric field
  • Primary metric output is always named value

12. Every File Explained

Entry & Server

src/index.ts

Entry point. Imports and starts the server. Nothing else.

src/server.ts

Creates the Express app. Applies CORS, JSON parsing (1MB limit), serves public/ as static files, mounts /api routes, adds /health endpoint. Starts listening on PORT (default 3000).

HTTP Layer — src/http/

src/http/api-router.ts

Express Router with 4 handlers: /meta, /inquiry, /report, /dashboard. Each handler: generates a runId, validates input with Zod, calls the analytics service, validates output with Zod, sets x-run-id header, sends JSON response. Catches and normalizes errors into Arabic error messages.

src/http/contracts.ts

All Zod schemas for requests and responses. Defines: promptRequestSchema, dashboardResponseSchema, reportResponseSchema, inquiryResponseSchema, reviewMetaSchema. If the API returns data that doesn't match these schemas, the response is rejected before sending.

Services — src/services/

src/services/analytics-service.ts

The central coordinator. Contains AnalyticsService class with methods: runInquiry(), runReport(), runDashboard(), getReviewMeta(). Handles: conversation memory, workflow execution with timeout, response shaping, auto-suggestion generation for /api/meta. Also generates Arabic UI suggestions from data store metadata using the Writer Agent (falls back to deterministic if LLM times out).

src/services/conversation-memory.ts

Three exported functions: resolveConversationRef() — creates or parses threadId/resourceId; buildConversationMemoryPrompt() — loads last 8 turns and formats them for the planning prompt; saveConversationExchange() — saves one user turn + one assistant turn to MongoDB. Content is truncated to 4000 chars.

Database — src/db/

src/db/mongo.client.ts

Creates and caches the MongoDB client. Exports getMongo() which returns { client, db }. Connects once and reuses the connection. Supports retry logic via MONGODB_CONNECT_RETRIES.

src/db/datastore.repository.ts

Exports dataStoreRepo — a singleton DataStoreRepository. Two methods: findDataStore(name) — finds one data store by name/collection/id; listAccessibleDataStores(scope) — returns only data stores the user's scope allows. Results are cached in memory — the MongoDB data_stores collection is only read once per process lifetime.

Mastra Registry — src/mastra/

src/mastra/index.ts

Registers all agents and workflows with the Mastra framework. Exports the mastra instance used throughout the app. Agents: supervisorAgent, mongodbAgent, searchAgent, writerAgent, chartPlannerAgent. Workflows: dashboardWorkflow, reportWorkflow, generalQuestionWorkflow.

src/mastra/model.ts

Exports resolveModel(role) — reads LLM_PROVIDER and returns the correct model instance. Supports per-role model overrides via environment variables. Default provider: openrouter. Default model: Llama 3.3 70B (free tier).

src/mastra/task-plan.ts

Exports finalizeTaskPlan() — the most important post-processing step. Takes the AI's raw TaskPlan and repairs it: normalizes field names, infers dimensions and filters from prompt text, resolves relative time ranges to absolute dates, infers topN, infers percentOf, ensures trend charts have a temporal dimension, clears metric for count aggregations.

Runtime Adapters — src/mastra/runtime/

src/mastra/runtime/supervisor-runtime.ts

Calls the Supervisor Agent. Loads data stores, sends compact metadata to the AI (only name, collection, field names/types/roles — no full documents), parses JSON response using parseJsonOutput(), calls finalizeTaskPlan(). Has 4-second timeout by default.

src/mastra/runtime/mongodb-runtime.ts

Two functions: runMongoDatasetQuery() for aggregations (dashboard/report) and runMongoRecordFetch() for raw records (inquiry). Both find the data store, build the pipeline deterministically, run it, validate rows, and return a clean Dataset.

src/mastra/runtime/chart-runtime.ts

Manages the agent-first chart system: for non-empty datasets it calls the Chart Planner Agent (3-second timeout), passes schema, up to 3 sample rows, row count, prompt, Supervisor hints, and candidate chart types, sanitizes the plan (strip invented fields, fix roles), merges explicit caller overrides, and builds the ECharts option. If planning fails, it falls back to deterministic rendering with Supervisor hints.

src/mastra/runtime/writer-runtime.ts

Calls the Writer Agent with the dataset and prompt. Returns parsed JSON with summary (inquiry) or reportSections (report).

src/mastra/runtime/search-runtime.ts

Calls the Search Agent when needsEnrichment=true. Passes: topic, joinKey, primarySchema, tenantId, timeRange. Returns enrichment Dataset with citations.

src/mastra/runtime/llm-queue.ts

Optional serialization queue for LLM calls. Set LLM_SERIAL_QUEUE=1 to prevent concurrent supervisor calls from overwhelming the LLM provider rate limits.

src/mastra/runtime/timeout.ts

Exports withTimeout(promise, name, ms) — wraps any async call with a time limit. Exports envTimeout(varName, default) — reads timeout from environment. All AI calls go through this.

src/mastra/runtime/json-output.ts

Exports parseJsonOutput(text, schema) — AI responses sometimes include markdown fences or extra prose. This function extracts the JSON substring and validates it against the Zod schema.

Tools — src/mastra/tools/

src/mastra/tools/mongodb-tools.ts

Three tool functions: buildAggregationFromPlan(plan, dataStore, scope) — validates then calls the pipeline builder; executePipeline(pipeline, collection, scope) — calls runAggregation with safety enforcement; validateRows(rows, dataStore) — normalizes types, builds schema and JSON Schema.

src/mastra/tools/chart-tools.ts

Exports buildChartFromDataset() — the deterministic ECharts option builder. Supports all 8 chart types. 16. How to Extend the App

Add a New Data Store

  1. Add metadata to MongoDB data_stores collection with correct field names, types, and roles
  2. Import records into the collection named by collection field in the metadata
  3. Include the data store name in scope.allowedDataStores
  4. Restart the server (metadata is cached — it won't auto-refresh)
  5. Test with GET /api/meta and dashboard prompts

Add a New Field to an Existing Data Store

  1. Add field to real MongoDB documents
  2. Add field metadata in data_stores (name, type, role)
  3. Choose correct role: dimension for group/filter, measure for numeric aggregation, temporal for date fields
  4. Restart server
  5. Test a prompt that uses the field

Add a New Prompt Filter Synonym (Arabic or English)

File: src/mastra/task-plan.ts

Add to inferPromptFilters() for new filter patterns, and to localizeEnumValue() for Arabic-to-English enum translations.

Add a New Dimension Alias

File: src/mastra/task-plan.ts

Add an entry to the aliases array in inferPromptDimensions():

{ pattern: /\bby\s+newfield\b/, field: 'newField' },
{ pattern: /حسب\s+الحقلالجديد/, field: 'newField' },

Add a New Chart Type

  1. Add to chartTypeSchema in src/mastra/schemas/chart.ts
  2. Add candidate selection logic in getChartTypeCandidates() in src/mastra/tools/chart-tools.ts
  3. Add rendering logic in buildChartFromDataset()
  4. Update chart planner agent instructions in src/mastra/agents/chart.ts
  5. Add Arabic label mapping in chartTypeLabel() in public/index.html

Add Production Authentication

  1. Add authentication middleware before API handlers
  2. Derive userId, tenantId, allowedDataStores, and rowFilter from the authenticated session
  3. Remove hardcoded SCOPE from public/index.html
  4. Keep the tenant guard in run-aggregation.ts as defense-in-depth

Vendor ECharts Locally (for Offline)

Replace the CDN script tag in public/index.html:

<!-- Replace this: -->
<script src="https://cdn.jsdelivr.net/npm/echarts@5.5.0/dist/echarts.min.js"></script>

<!-- With this (after copying file to public/): -->
<script src="/echarts.min.js"></script>

19. Team Presentation Script

30-Second Version

What to say This app is a natural-language analytics service for the Mind Platform. A user asks a question — in Arabic or English. The Supervisor AI converts it into a structured plan. The backend builds a safe MongoDB query from that plan. The result becomes a dashboard chart, a written report, or a search summary. The key point: the AI plans, but TypeScript code validates and executes the database query. The LLM never writes raw database code.

2-Minute Version

The app has three modes. Dashboard returns one chart. Report returns Arabic analytical text and optionally a chart. Inquiry returns a summary and record links.

The UI is a single review console. Suggestion buttons are generated from the actual MongoDB data — not static examples. When a user submits a prompt, the backend adds conversation memory if it's a follow-up, then starts a Mastra workflow.

The Supervisor Agent creates a TaskPlan. A finalizer normalizes it — removing bad fields, inferring "by municipality" as a dimension, resolving "last 30 days" to actual dates. Then the MongoDB runtime builds a deterministic aggregation pipeline, stage by stage: match (with tenant guard), group, sort, limit. The executor enforces safety: blocks dangerous stages, limits pipeline length, sets a timeout.

For dashboard output, the Chart Planner Agent chooses how to map fields, and deterministic code builds the ECharts configuration. For report and inquiry output, the Writer Agent writes Arabic text grounded only in the returned data.

The audit panel is the best feature for technical review — it shows the TaskPlan, MongoDB pipeline, schema, and timing for every request.

Expected Questions & Answers

QuestionAnswer
Is this production-ready?Not fully. It is a solid analytics prototype. Production needs real authentication, server-derived permission scope, a proper frontend shell (Angular), and operational hardening.
Does the LLM write MongoDB queries?No. The LLM creates a structured TaskPlan JSON. TypeScript builders in src/analytics/builders/ convert that to MongoDB stages safely.
Can it support more data collections?Yes. Add a data store definition with correct field metadata and the AI can use it automatically — no hardcoded logic needed.
Can it answer questions using external/web data?No. The Search Agent is internal-only. It searches exported platform knowledge, not the public web.
Why is the report text in Arabic?The Writer Agent and UI are Arabic-oriented for Qatar municipal review. This can be changed by updating writer instructions and UI copy.
Where do the prompt suggestions come from?From /api/meta, generated from real data store field metadata. Not static hardcoded examples.
What happens if the AI gives a wrong field name?finalizeTaskPlan() strips unknown fields and the validators reject invalid ones before the pipeline runs. The app never queries a field that doesn't exist in the metadata.
How does follow-up conversation work?After each request, the user's question and the app's answer are saved to MongoDB. For the next request, the last 8 turns are loaded and included in the planning prompt so the Supervisor understands context.

What to Emphasize to the Manager

  • Metadata-driven design — add any new data store with proper metadata and the AI can use it, no code changes needed
  • Safety-first query execution — the LLM plans, TypeScript validates and executes, tenant filtering is always enforced
  • Transparent AI — the audit panel shows exactly what the AI decided and what the database received
  • Full Arabic support — reports, summaries, UI labels, prompt suggestions all in Arabic
  • This is a prototype / review console — not the full production Mind Platform
  • Production needs: real auth, Angular frontend, NestJS gateway, server-derived scope
