What the App Does
Purpose, outputs, and the two applications

A user types a question in Arabic or English — e.g. "top 5 municipalities by budget" — and MindAI responds with one of three output types:

📊
Dashboard
Interactive ECharts visualizations — bar, line, donut, scatter, heatmap and more — rendered from real MongoDB data.
📄
Report
Structured 1–5 section analytical narrative: Overview → Findings → Breakdown → Trends → Recommendations.
💬
Inquiry
A direct 1–3 sentence factual answer, leading with the key number from the data.
🧠
Memory
The system remembers user goals and preferences across sessions automatically — no configuration required.

Full Request Lifecycle
Every step for: "show top 5 projects by budget" on the Dashboard tab
1
Browser — User clicks Send → POST /api/analytics { prompt, intent: "dashboard", sessionId }
↓
2
AnalyticsController — validates DTO via NestJS ValidationPipe, calls AnalyticsService.run()
↓
3
API Key — look up per-user key in MongoDB → fall back to global .env key → throw 401 if neither
↓
4
Session — sessionExists(id) checks LibSQL → reuse existing session or create new UUID
↓
5
Session context — getMemoryContext(sessionId) → last 6 conversation turns from LibSQL → CoreMessage[]
↓
6
Long-term memory — embed prompt (local WASM, 384-dim) → cosine search MongoDB memory_items → top-3 relevant facts → prepended to context as fake prior messages
↓
7
Route by intent → PipelineService.executeDashboard()
↓
8
Full dashboard cache check — SHA-256("dashboard:full:" + prompt) → MongoDB lookup → HIT: return immediately, 0 LLM calls
↓ (cache MISS — continue)
9
Aggregation cache check — SHA-256("dashboard:" + prompt) → another MongoDB lookup → HIT skips planner LLM
↓ (aggregation cache MISS — continue)
10
🤖 LLM #1 — Planner (70B, ≤600 tokens) — outputs TaskPlan: MongoDB pipeline JSON + sourceName + strategy + chartHint
↓
11
Pipeline safety check — reject $function / $merge / $out / $where / $eval before execution
↓
12
MongoDB aggregation — run the pipeline against the real collection → rows[]
↓
13
Check plan.skills.includes('chart') — if false (conversational question) → fallback to executeInquiry()
↓
14
🤖 LLM #2 — Chart (70B, ≤1000 tokens) — outputs widget plan: chart types + field names + optional ECharts override
↓
15
TypeScript renderers — validate fields → deterministic ECharts option generation → deepMerge any chartOptions override → DashboardSpec
↓
16
HTTP response — { intent: "dashboard", chart: DashboardSpec, sessionId, messageId } — sent to browser
↓
17
Angular — state update → ngAfterViewChecked detects new [data-widget-id] elements → echarts.setOption(widget.option) → charts render
↓ (fire-and-forget after HTTP response sent)
18
Background — save turn to LibSQL + 8B LLM extracts 0–3 facts → embed → upsert to MongoDB memory_items + write to history + cache

NestJS Backend — All Modules
Every module, service, and what it owns

AnalyticsModule — The Core

FileWhat It Does
analytics.service.tsOrchestrator. API key resolution → session → memory → route by intent → error classification → fire-and-forget saves
pipeline.service.tsWorker. Runs aggregation + all three executors (dashboard, report, inquiry). Calls all AI functions.
analytics.controller.tsPOST /api/analytics — validates DTO, extracts userId from x-user-id header

The error classification in analytics.service.ts handles two special cases automatically:

  • Invalid API key — if the per-user key is bad and a global key exists, it auto-deletes the per-user key and retries with the global key
  • Rate limit (429) — extracts "try again in Xm Ys" from the Groq error message and returns it as a clean user-facing string

CacheModule

FileWhat It Does
cache.service.tsgetCached<T>(intent, prompt) / setCached(intent, prompt, value) — key = SHA-256 of intent+prompt
prompt-cache.tsMongoose schema. TTL index on createdAt — MongoDB auto-deletes records after 7 days

Two cache levels exist:

  • Aggregation cache (key = "dashboard:prompt") — stores { plan, rows }, skips planner LLM
  • Full dashboard cache (key = "dashboard:full:prompt") — stores complete DashboardSpec, skips both LLM calls and MongoDB aggregation

Cache is bypassed when context.length > 0 (multi-turn conversation) because the result depends on prior messages.

Planner — Supervisor LLM (ai/planner.ts)

Called once per request. Converts natural language prompt + available data sources → structured TaskPlan.

// Input to LLM
{ prompt: "top 5 municipalities by budget", intent: "dashboard" }

// LLM Output (Zod-validated)
{
  needsData: true,
  query:     { sourceName: "municipalities" },
  pipeline:  [
    { "$group": { "_id": "$name", "total": { "$sum": "$budget" } } },
    { "$sort":  { "total": -1 } },
    { "$limit": 5 }
  ],
  strategy:  "standard",
  chartHint: "ranking"
}

Skill derivation — deriveExecutionSkills() computes plan.skills from the plan:

Conditionplan.skills result
needsData: false[] — conversational, no data needed
intent = dashboard['aggregation', 'chart']
intent = report + wantChart['aggregation', 'report', 'chart']
intent = report only['aggregation', 'report']
intent = general_question['aggregation', 'inquiry']

The skills array controls exactly which downstream functions run — nothing else.

Chart Skill — Hybrid Architecture (ai/chart.ts)

The most complex file. Uses a hybrid approach: LLM decides what to show, TypeScript decides how to render it.

Three Output Modes

ModeLLM OutputsTypeScript DoesWhen Used
Standardchart type + field namesDeterministic renderer builds full ECharts option from real dataMost charts (bar, line, donut…)
+ chartOptionsSame + partial ECharts overrideRender base → deepMerge(base, chartOptions)Custom colors, tooltips, marklines
customFull ECharts option in chartOptionsrenderCustom() returns {option:{}} → deepMerge gives {option: chartOptions}Mixed charts, anything a standard renderer can't handle

Validation Pipeline

1
LLM returns LlmDashboard — Zod validates schema (type enum, field names are strings, no .max() on widget count)
2
Slice to MAX_WIDGETS (default 3) in code — not in Zod (avoids silent rejection)
3
validateWidget() — for non-custom: check field names exist in data keys, valueField is numeric
4
toWidgetPlan() — auto-detect missing valueField by scanning data for first numeric column
5
renderWidget() → call the TypeScript renderer for the chart type → ECharts option
6
mergeChartOptions(rendered, plan.chartOptions) → deep-merge LLM override on top

Memory Skill (ai/memory-skill.ts)

Runs fire-and-forget after every response. Extracts 0–3 structured facts per turn.

// Extracted format
[
  { type: "preference", content: "User focuses on health sector", tags: ["health"], importance: 4 },
  { type: "goal",       content: "Tracking Q1 budget utilization", tags: ["budget"], importance: 5 }
]

Types: goal | insight | preference | context | decision. Importance: 1–5 scale.

Uses llama-3.1-8b-instant — this is pure JSON extraction, not reasoning. Runs against a separate 6,000 TPM pool from the 70B models.

Embeddings (ai/embeddings.ts)

PropertyValue

The server is fully functional during the background warmup. Memory retrieval degrades gracefully (returns empty string) until the model is ready.

Two-Layer Memory System
Short-term session memory + long-term cross-session memory
⚡
Layer 1 — Session Memory (LibSQL)
Last 6 conversation turns per session. Fast local SQLite. Enables follow-up questions like "show me just the top 3". Scoped to one browser session.
🧠
Layer 2 — Long-Term Memory (MongoDB)
Structured facts extracted after every response. Persists across sessions, across browser restarts. Retrieved by semantic similarity. Makes the AI remember user goals and preferences.

Session Memory — LibSQL / SQLite

File: session/memory.ts — Mastra Memory class with LibSQLStore

FunctionDescription
ensureThread(id, title, intent)Creates a new LibSQL thread or updates an existing one. Never throws — silently swallows errors.
sessionExists(id)Returns true/false — used to decide whether to reuse an incoming sessionId
getMemoryContext(id)Returns last 6 messages as CoreMessage[] for injection into LLM context
saveConversationTurn()Writes both user + assistant messages to LibSQL in one saveMessages() call

Each stored message has two text representations:

  • content.parts[0].text — plain text summary (what the LLM sees as context)
  • content.metadata.uiMessage — full typed ConversationMessage with the complete dashboard/report/inquiry result (what the Angular history sidebar displays)

Long-Term Memory — MongoDB

Files: memory/memory.service.ts + memory/memory.repository.ts

// WRITE PATH (after every response, fire-and-forget):

Key Design Decisions
Every major technical choice with the reasoning behind it
DecisionWhat Was ChosenWhy
LLM temperature0 on all callsSame prompt = same output = cacheable, reproducible, debuggable. Non-zero temperature would break the 7-day cache.
Chart architectureHybrid C: LLM picks fields, TypeScript renders EChartsFull LLM output (Approach B) costs 3× more tokens and risks invalid JSON. Pure deterministic (Approach A) is inflexible. Hybrid: best of both. Custom escape hatch handles everything else.
Schema in planner promptFull field list injected per sourceLLM can only reference field names that exist in the data. Prevents hallucinated field names in MongoDB pipelines that would crash at runtime.
Cache bypass on multi-turnSkip cache when context.length > 0"Show me just the top 3" depends on what was returned previously. Returning the cached top-5 would be wrong.
Fire-and-forget writesCache, history, memory all async after responseNever block the HTTP response. User gets their answer in <3 seconds regardless of write speed or failures.
8B for memory extractionllama-3.1-8b-instant for memory roleRuns after every response. Using 70B adds ~700 tok/req to the 70B 6,000 TPM pool → quota exhaustion under load. 8B has its own pool.
Local WASM embeddings@xenova/transformers — no APIMemory retrieval works with zero API quota. 384-dim vectors generated entirely locally, no latency from external calls.
No silent .catch() on chartAll chart errors throw and surfaceOld code returned empty widgets with "Chart planning failed" text — confusing with no actionable information. Now all errors reach the user.
Dashboard → inquiry fallbackConversational questions on Dashboard tab route to inquiryPlanner returns needsData:false, skills:[] for "what did we find last time?". Old code threw "no chart path". Now routes to inquiry and answers from memory context.
Pipeline safety guardsReject $function/$merge/$out/$where/$evalLLM-generated pipelines could otherwise modify data or execute arbitrary JavaScript inside MongoDB.
RequestIdMiddlewareAsyncLocalStorage 8-char ID per requestWithout it, logs from parallel requests are interleaved and impossible to trace. Single grep by ID shows the complete flow.
Zod for LLM outputgenerateObject() with strict schemasLLM output that doesn't match the schema triggers an automatic retry rather than a runtime crash. Field types and enum values are enforced before any code touches the data.
Two database typesLibSQL for sessions, MongoDB for everything elseLibSQL: zero-setup local SQLite, perfect for ordered conversation turns. MongoDB: persistent, queryable across users, supports array fields for embeddings.
No .max() on widget countSlice to MAX_WIDGETS in code, not in ZodZod .max(3) would silently reject the entire LLM response if it returned 4 widgets. The fix: accept any count from Zod, slice to 3 in application code.
