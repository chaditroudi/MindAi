1. Overview

Mind Viz Agents is a TypeScript and Node.js analytics service for Mind Platform. It lets a user ask natural-language questions and receive a dashboard chart, structured report, or inquiry summary.

What the app does Turns prompts into structured analytics output using Mastra workflows, LLM agents, MongoDB, and ECharts.
Current demo domain Qatar municipal operations: service requests, inspections, permits, and projects.
Important design The LLM creates a plan. Backend code builds and executes the actual MongoDB query.

2. Architecture

Browser UI or API client
  -> Express API route
  -> AnalyticsService
  -> Mastra workflow
  -> Supervisor Agent creates TaskPlan
  -> MongoDB runtime builds and executes safe aggregation pipeline
  -> Optional search enrichment
  -> Writer Agent or Chart runtime
  -> JSON response
Key idea: The LLM does not directly query MongoDB. It returns structured JSON. The backend validates and translates that JSON into a safe pipeline.

3. Runtime Request Flow

  1. User selects dashboard/report/inquiry and enters a prompt.
  2. Frontend sends { prompt, scope } to the selected endpoint.
  3. Express validates the request.
  4. AnalyticsService starts the matching Mastra workflow.
  5. Supervisor creates a TaskPlan.
  6. finalizeTaskPlan normalizes fields, filters, dates, and chart hints.
  7. MongoDB runtime resolves the selected Data Store.
  8. buildAggregationFromPlan() creates the MongoDB pipeline.
  9. executePipeline() runs the query with tenant guard.
  10. Writer/chart/search steps format the result.
  11. Frontend renders chart, report, summary, or error.

4. JSON Export vs Runtime MongoDB Query

The JSON export under samples/db-export is not the live database query. It is a static knowledge/schema corpus. The real MongoDB query is generated at runtime.

Item Purpose Where
JSON export Knowledge context: collections, fields, row counts, sample values. samples/db-export
TaskPlan LLM interpretation of prompt into query intent. src/mastra/schemas/intent.ts
MongoDB query Runtime aggregation pipeline built by backend code. buildAggregationFromPlan()
Audit pipeline Visible generated query pipeline for dashboard responses. audit.pipeline 
User prompt
  -> TaskPlan from LLM
  -> buildAggregationFromPlan()
  -> MongoDB aggregation pipeline
  -> executePipeline()
Current gap: dashboard exposes audit.pipeline. Report and inquiry expose audit.plan and elapsedMs, but not the executed pipeline yet.

The UI is a static page in public/index.html. It is a demo/review interface, not a production frontend shell.

UI Request Lifecycle

User clicks تشغيل
  -> run()
  -> startProgress()
  -> fetch(currentEndpoint, { prompt, scope })
  -> backend workflow runs
  -> render(data)
  -> audit panel prints data.audit
  -> resetControls()

Important UI Variables

SCOPE Demo-only scope sent with the request. Production must derive this server-side.
currentEndpoint Stores the selected workflow endpoint.
EXAMPLES Stores endpoint-specific placeholders and example prompts.
PROGRESS_STAGES Stores estimated UI progress stages per endpoint.

Rendering Rules

  • Dashboard: render data.chart.option with ECharts.
  • Report: render data.reportSections and optional first chart.
  • Inquiry: render data.summary and data.recordLinks.
  • Error: hide chart and show error message.
Progress is estimated client-side. The backend currently returns only final JSON, not live workflow events.

7. Agents

Supervisor Agent Classifies intent and creates the TaskPlan.
MongoDB Agent Optional audit/notes path. Deterministic runtime is source of truth for data.
Search Agent Uses web search or internal knowledge retrieval for enrichment.
Writer Agent Writes inquiry summaries and report sections as strict JSON.
Chart Agent Improves chart title, annotations, and accessibility metadata.

13. Errors

Invalid JSON response

Mastra asked the model for structured JSON, but the provider returned invalid or non-JSON output.

Provider returned error

OpenRouter or the selected provider failed, timed out, rate-limited, rejected the model, or returned an error body.

Slow button/result

The workflow can call multiple LLM/provider steps. The UI progress exists to show users that the app is still working.

14. Security

  • Tenant guard is inserted into MongoDB pipeline.
  • Execution path checks tenant guard again.
  • Blueprint access is limited by allowedBlueprintIds.
  • Rows are normalized before downstream agent use.
Production gap: the demo currently accepts scope from the browser. In production, scope must come from auth middleware.

16. Manager Answers

Where is the query?

The query is generated at runtime from the TaskPlan. It is built in buildAggregationFromPlan(). Dashboard exposes it in audit.pipeline.

Why do we have JSON export?

The JSON export is only knowledge/schema context. It helps the app understand collections and fields. It is not the live query.

Why is the button sometimes slow?

The request can involve several LLM calls, MongoDB query execution, optional search enrichment, and retry after invalid JSON.

Is this production-ready?

It is a strong prototype/demo. Before production, move scope to auth middleware, add tests, timeouts, tracing, and backend progress streaming.

17. Recommended Next Steps

  1. Expose audit.pipeline for report and inquiry.
  2. Move request scope from browser body to auth middleware.
  3. Reduce LLM payload sizes, especially chart metadata calls.
  4. Add tests for tenant guard and TaskPlan-to-pipeline conversion.
  5. Add backend progress streaming with SSE, WebSocket, or polling.
  6. Add copy/export buttons for plan, pipeline, report, chart PNG, and ECharts option JSON.
  7. Add request timeout and retry policy.
  8. Add structured tracing with run IDs across all workflow steps.
