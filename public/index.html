توثيق الواجهة للفريق

هدف الصفحة وطريقة استخدامها
الغرض هذه صفحة مراجعة محلية لاختبار مسارات التحليلات: لوحة المعلومات، التقرير، والاستعلام.
التقنية الصفحة ملف واحد: public/index.html. لا يوجد React أو build frontend. يتم تحميل ECharts من CDN.
مهم هذه ليست واجهة إنتاجية. هي أداة demo/review لعرض النتائج وفحص الـ audit.
أجزاء الواجهة
  • التبويبات: تختار endpoint: /api/dashboard أو /api/report أو /api/inquiry.
  • مربع النص: يرسل prompt المستخدم إلى backend.
  • أمثلة جاهزة: تتغير حسب التبويب وتستدعي الطلب مباشرة عند الضغط.
  • منطقة التقدم: تعرض مراحل تقديرية ووقت الانتظار أثناء تنفيذ workflow.
  • منطقة النتيجة: تعرض chart أو report sections أو inquiry summary أو error.
  • لوحة التدقيق: تعرض data.audit كما يرجع من API.
مسار الطلب من الواجهة إلى الباكند
User clicks تشغيل -> run() -> startProgress() -> fetch(currentEndpoint, { prompt, scope }) -> backend workflow runs -> frontend receives final JSON -> render(data) -> audit panel prints data.audit -> resetControls()
  • currentEndpoint يحدد أي workflow سيتم استدعاؤه.
  • SCOPE موجود داخل الصفحة لأغراض demo فقط.
  • في الإنتاج يجب أن يأتي scope من authentication في السيرفر، وليس من المتصفح.
قواعد عرض النتائج
Dashboard يعرض data.chart.option داخل ECharts ويخفي النصوص. الـ audit يحتوي على plan و pipeline و elapsedMs.
Report يعرض data.reportSections، وإذا وجدت charts يعرض أول chart. حالياً audit يعرض plan و elapsedMs.
Inquiry يخفي الرسم، ويعرض summary وروابط السجلات. حالياً audit يعرض plan و elapsedMs.
التحميل والتقدم
  • التقدم المعروض في الواجهة تقديري client-side وليس streaming من الباكند.
  • الـ API يرجع final JSON فقط بعد انتهاء workflow.
  • PROGRESS_STAGES يحتوي مراحل مختلفة لكل endpoint.
  • عند بدء الطلب يتم تعطيل الزر، مربع النص، التبويبات، وأزرار الأمثلة لمنع طلبات مكررة.
  • للحصول على تقدم حقيقي لاحقاً نحتاج SSE أو WebSocket أو polling باستخدام runId.
لوحة التدقيق: أين الخطة وأين query؟
  • audit.plan هو TaskPlan الناتج من LLM بعد التطبيع.
  • audit.pipeline هو MongoDB aggregation pipeline الحقيقي، وهو ظاهر حالياً في dashboard فقط.
  • الـ JSON export ليس query. هو knowledge/schema context فقط.
  • الـ query الحقيقي يتم إنشاؤه في backend داخل buildAggregationFromPlan().
  • إذا أضفنا audit.pipeline للتقرير والاستعلام، هذه الواجهة ستعرضه تلقائياً لأنها تطبع audit كامل.
أهم متغيرات ودوال JavaScript
SCOPE صلاحيات demo المرسلة مع الطلب. لا تستخدم بهذا الشكل في الإنتاج.
EXAMPLES أمثلة و placeholders لكل endpoint.
PROGRESS_STAGES مراحل التقدم التقديرية لكل workflow.
run() الدالة الرئيسية التي ترسل الطلب وتعرض النتيجة أو الخطأ.
render(data) تختار طريقة العرض حسب data.intent.
escape() تمنع إدخال HTML غير آمن عند عرض نصوص الLLM أو الأخطاء.
قيود الواجهة الحالية وخطوات التطوير
  • لا يوجد login أو session في الواجهة.
  • لا يوجد زر إلغاء الطلب أثناء التنفيذ.
  • لا يوجد history للطلبات السابقة.
  • لا يوجد export للـ chart أو report من الواجهة.
  • كل الكود داخل ملف HTML واحد، وهذا مناسب للdemo فقط.
  • أفضل تحسينات قادمة: backend progress حقيقي، copy buttons للplan/pipeline، export chart PNG/JSON، واستبدال SCOPE hardcoded بمستخدم حقيقي.
