Project Overview & Stack
What MindAI is, how it's structured, and what it's built with

MindAI is an AI-powered analytics platform that accepts natural language prompts and returns interactive dashboards, structured reports, or factual answers backed by real data from MongoDB. Users can ask questions like "show me the top 5 municipalities by budget" and get a fully rendered ECharts visualization with insights.

3.3 Analytics Service — Core Orchestrator

nest-app/src/analytics/analytics.service.ts

The AnalyticsService.run() method is the central entry point for every user query. It orchestrates:

1
API Key Resolution — per-user key → global env key → 401 if neither
2
Session Management — create/reuse LibSQL thread, load last 6 messages
3
Long-Term Memory — embed prompt → cosine search → inject top-3 memories as context
4
Intent Routing → dashboard / report / inquiry / free-text (Mastra agent)
5
Error Handling — invalid key auto-retry with global, rate limit → 429 + retry-after
6
Save Session Turn — fire-and-forget write to LibSQL
7
Extract Memories — fire-and-forget extraction via 8B model → save to MongoDB

4.3 Chart Skill — 100% Deterministic Code

nest-app/src/ai/chart.ts
⭐
Key Design: No LLM for Dashboard Charts The chart skill is entirely deterministic TypeScript code. Given data rows + a chart hint, it analyzes the data shape, picks the right chart type, assigns fields, and generates a complete ECharts configuration — no LLM call required.

The chart pipeline runs in 5 deterministic steps:

1
analyzeDataShape(rows) — Detect: grouped_pairs, time_series, scatter_capable, multi_field
2
reconcileChartHint(hint, shape) — Downgrade invalid hints (e.g. scatter without XY data → distribution)
3
determineChartType(shape, hint, rowCount) — Pick: bar, line, donut, scatter, kpi, table
4
assignFields(shape, type) + computeInsight(rows) — Map data columns to chart axes
5
renderWidget(plan, rows) — Generate complete ECharts option object

Stores the last 6 conversation turns. Fast local SQLite. Scoped to a single browser session. Gives the AI context for follow-up questions.

Extracts structured insights after every response. Persists across sessions. Retrieved via embedding similarity. Makes the AI remember your preferences and goals.

How tokens are allocated and how rate limits are managed

Groq Free Tier Limits

⚠️
Why memory uses 8B model Memory extraction runs after every response, adding ~700 tokens to the 70B budget per request. Using 8B for this background task keeps the 70B budget at ~2,600 tokens/request — well within the 6,000 TPM limit with room for retries.

Rate Limit Handling

  • maxRetries: 1 on all LLM calls — Vercel AI SDK automatically retries 429s with exponential backoff
  • Rate limit errors propagate to the Angular UI with the full error message including retry-after duration
  • No silent fallbacks — all chart/writer errors throw and surface to the user
  • Cache-first: identical prompts never hit the LLM twice (7-day TTL)

Cache System
Two-level caching to minimize LLM calls
🗄️
Aggregation Cache
Caches { plan, rows } for any intent. Hit = 0 LLM calls for supervisor + MongoDB query skipped.
📊
Dashboard Full Cache
Caches the complete DashboardSpec. Hit = 0 LLM calls + 0 MongoDB queries. Instant response.

Cache Key Generation

key = SHA-256(intent + ":" + normalize(prompt)).slice(0, 24)

normalize(prompt) = prompt.trim().toLowerCase().replace(/\s+/g, ' ')

Cache Bypass Rules

ConditionBypass?Reason
context.length > 0 (multi-turn)✅ Always bypassContext-dependent answers must not be cached
Single-turn, same prompt❌ Use cacheSafe to serve cached result
Different userId, same prompt❌ Use cachePrompt cache is userId-independent

Storage

  • Collection: prompt_cache in MongoDB
  • TTL: 7 days (MongoDB TTL index on createdAt)
  • Hit tracking: increments hitCount + updates lastHitAt on every cache hit
  • Write: fire-and-forget (never blocks HTTP response)

Key Design Decisions
Why the system is built the way it is
DecisionWhy
Temperature: 0 on all LLM callsReproducible pipelines — same prompt always gives same MongoDB query
Dashboard chart = deterministic code (no LLM)Eliminates a full LLM call per dashboard. No hallucinated field names. Instant rendering.
Schema injected into system promptLLM can only reference field names that actually exist in the data source
Cache bypassed on multi-turnFollow-up questions depend on conversation context, not just the prompt text
Fire-and-forget writes (history, cache, memory)Never block the HTTP response. User gets their answer immediately.
LibSQL for sessions, MongoDB for long-termLibSQL: fast local SQLite for active conversations. MongoDB: persistent, queryable, indexed.
Local WASM embeddings (no API)Memory retrieval works without any API quota. 384-dim vectors stored in MongoDB alongside documents.
Memory model = 8B (not 70B)Background JSON extraction task. Doesn't need reasoning quality. Saves ~700 tokens/request from 70B budget.
maxRetries: 1 on LLM callsGroq SDK automatically backs off on 429. One retry handles transient errors without manual logic.
No silent fallbacks on chart errorsSilent fallbacks produced "Chart planning failed" UI with no actionable feedback. Now errors propagate clearly.
Pipeline safety guards ($function, $merge, etc.)Prevent LLM from generating queries that modify data or execute arbitrary code in MongoDB
RequestIdMiddleware (AsyncLocalStorage)Every log line for a single request shares the same 8-char ID — easy to trace requests in logs
Per-user API keys in MongoDBEach user can bring their own Groq key. Falls back to global key if none provided.
Zod schema for all LLM outputVercel AI SDK enforces schema via generateObject(). Invalid LLM output triggers a retry, not a crash.
🚀
Summary MindAI converts natural language to data-driven dashboards using a 3-stage pipeline: (1) Supervisor LLM plans a MongoDB aggregation, (2) MongoDB executes it, (3) deterministic code renders the chart — all in under 3 seconds on cache miss. Memory, caching, and session context make the system progressively smarter with every interaction.
