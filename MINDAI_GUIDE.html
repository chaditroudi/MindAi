What Is MindAI?
Purpose, what it does, and how it feels to use it

MindAI is an AI-powered municipal analytics platform. Users type questions in plain Arabic or English — like "show me the top 5 municipalities by budget" or "summarize high-priority projects" — and the system responds with:

📊
Dashboard
Interactive ECharts visualizations (bar, line, donut, scatter, heatmap…) generated from real MongoDB data.
📄
Report
Structured 1–5 section analytical narrative with optional charts.
💬
Inquiry
Direct 1–3 sentence factual answer pulled from data.
🧠
Memory
Remembers user goals and preferences across sessions automatically.

3.3 Analytics Service — The Orchestrator

File: analytics/analytics.service.ts · Method: run(req)

Every single user query flows through this method in order:

1
Validate prompt — Zod: min 1 char, max 1000 chars
2
Resolve API key — per-user MongoDB key → global env key → 401 if neither
3
Session management — reuse session if valid ID exists in LibSQL, else create new UUID
4
Load session context — getMemoryContext() returns last 6 messages from LibSQL
5
Long-term memory — embed prompt → cosine search → inject top-3 memories as fake prior messages
6
Route by intent — dashboard / report / inquiry / free-text agent
7
Error handling — invalid key → auto-retry with global key · 429 rate limit → user-friendly message
8
Fire-and-forget — save turn to LibSQL + extract memories to MongoDB (never blocks response)

3.4 Pipeline Service — LLM + MongoDB Execution

File: analytics/pipeline.service.ts

MethodIntentLLM CallsWhat Happens
executeDashboard()dashboard1 (planner) + 1 (chart)Plan → aggregate → chart render → cache full result
executeReport()report1 (planner) + 1–2 (writer ± chart)Plan → aggregate → writer + chart in parallel
executeInquiry()inquiry1 (planner) + 1 (writer)Plan → aggregate → writer (1–3 sentence answer)
aggregate()(shared)1 (planner)Cache check → planner → safety check → MongoDB aggregate → flush to history
⚠️
Pipeline Safety: These MongoDB operators are always rejected before execution: $function, $merge, $out, $where, $eval. They would allow arbitrary code execution or data modification.
💡
Dashboard → Inquiry Fallback: When a user asks a conversational question on the Dashboard tab (e.g., "What did we find last time?"), the planner returns needsData: false and skills: []. Instead of throwing an error, the pipeline falls back to executeInquiry() which answers from memory context.

4.2 Planner — Supervisor LLM

File: ai/planner.ts · Called once per request

Converts a natural language prompt + available data sources → structured TaskPlan with a MongoDB aggregation pipeline.

// Input to LLM
{ prompt: "top 5 municipalities by budget", intent: "dashboard" }

// LLM Output (Zod-validated)
{
  needsData: true,
  query: { sourceName: "municipalities" },
  pipeline: [
    { "$group": { "_id": "$name", "total": { "$sum": "$budget" } } },
    { "$sort": { "total": -1 } },
    { "$limit": 5 }
  ],
  strategy: "standard",
  chartHint: "ranking"
}
ParameterValueWhy
Max tokens600Planner output is small JSON — 600 is enough and saves quota
ModejsonForces Groq to return raw JSON without markdown wrappers
Schema injectionFull field definitions per sourceLLM can only reference fields that actually exist in the data
ContextLast 6 session messagesEnables follow-up queries ("show me just the top 3")

4.3 Chart Skill — Hybrid Architecture (Approach C)

File: ai/chart.ts · Prompt: skills/chart/SKILL.md

⭐
Key Design: The chart skill is a hybrid — the LLM decides WHAT to show (chart type, field mapping, customizations), but TypeScript code decides HOW to render it (ECharts option generation). This gives flexibility without wasting tokens.

Three Output Modes

ModeWhen LLM Uses ItWhat LLM OutputsWhat TypeScript Does
StandardMost charts (bar, line, donut…)type + field names (labelField, valueField)Deterministic renderer builds full ECharts option from real data
+ chartOptionsNeeds custom colors/tooltip/marklinesSame + partial ECharts override objectRender base → deepMerge(base, chartOptions)
customMixed or unusual chart (bar+line combo)Full ECharts option in chartOptionsPass through directly to ECharts

Validation Flow

After the LLM returns a plan, TypeScript validates it before rendering:

1
Field name check — reject any widget where labelField/valueField/xField don't exist in the real data
2
Numeric check — valueField must be a number column (unless agg: "count")
3
Auto-detect valueField — if LLM forgot to set it, scan data for first numeric column
4
Render — call the TypeScript renderer for the chart type → produce ECharts option
5
deepMerge — merge chartOptions override on top of the rendered base

Files: memory/memory.service.ts · memory/memory.repository.ts

// After every response (background):
memory.extractAndSave(userId, sessionId, prompt, summary, apiKey)
  → 8B LLM extracts 0–3 facts from the conversation
  → embed each fact to 384-dim vector
  → upsert to MongoDB memory_items collection

// Before every request (inline):

  → injected into planner context as "prior session knowledge"

9.1 Groq Free Tier Limits

~600 tok
Planner output
≤600 tok
Chart input
~500 tok
Chart output
≤1000 tok
Total 70B
~2,600 tok

Leaves ~3,400 tokens of buffer per minute. With caching, most repeat queries cost 0 tokens.

9.3 Why Memory Uses 8B Not 70B

⚠️
Critical configuration decision: Memory extraction fires after EVERY response. If it used the 70B model, it would add ~700 tokens to the 70B budget per request: 2,600 + 700 = 3,300 total. Under load (multiple users), this hits the 6,000 TPM limit very quickly. The 8B model does the same JSON extraction job at the same cost but against a completely separate TPM pool.

9.4 Cache Impact

The prompt cache (MongoDB, 7-day TTL) is the most effective optimization. When a cache hit occurs:

  • 0 calls to the planner LLM
  • 0 calls to MongoDB aggregation
  • 0 chart LLM calls (full dashboard cache)
  • Response in < 50ms instead of < 3 seconds

Cache is bypassed only for multi-turn conversations (context-dependent queries cannot be cached).

DecisionWhat Was ChosenWhy
LLM temperature0 on all callsSame prompt → same MongoDB pipeline every time. Reproducible, cacheable, debuggable.
Chart skill architectureHybrid: LLM picks fields → TypeScript renders EChartsFull LLM ECharts output (Approach B) costs ~3× more tokens and risks invalid configs. Deterministic only (Approach A) is inflexible. Hybrid gives quality + efficiency + customization via chartOptions.
Schema in planner promptFull field list injected per sourceLLM can only reference field names that actually exist. Prevents hallucinated field names in MongoDB pipelines.
Cache bypass on multi-turnSkip cache when context.length > 0"Show me the top 3 instead" depends on the previous response. Caching would return the cached top 5.
Fire-and-forget writesCache, history, memory all asyncNever block the HTTP response. User gets their answer in <3s regardless of write speed.
Two database typesLibSQL for sessions + MongoDB for everything elseLibSQL: fast local SQLite, perfect for ordered conversation turns. MongoDB: persistent, queryable, supports vector search for embeddings.
Local WASM embeddings@xenova/transformers (no API)Memory retrieval works with zero API quota. 384-dim vectors cost ~0 to generate locally.
Memory model = 8Bllama-3.1-8b-instant for memory roleBackground JSON extraction doesn't need reasoning quality. Saves ~700 tokens/request from the 70B 6,000 TPM budget.
No silent fallbacksAll LLM errors throw and surface to userSilent .catch() fallbacks were returning empty widgets with "Chart planning failed." message — confusing users with no actionable information.
Dashboard → inquiry fallbackConversational questions on Dashboard tab route to inquiryUsers ask "what did we find last time?" in the Dashboard tab. Instead of throwing "no chart path", the system answers from memory context as text.
Pipeline safety guardsReject $function, $merge, $out, $where, $evalLLM-generated pipelines could otherwise modify data or execute arbitrary JavaScript in MongoDB.
RequestIdMiddlewareAsyncLocalStorage request ID on every log lineWithout it, logs from parallel requests are interleaved and impossible to trace. 8-char ID makes grep trivial.
Per-user API keysMongoDB storage per userIdMultiple users can bring their own Groq key. Global key is the fallback. Invalid per-user key auto-deletes and retries with global key.
Zod schema for LLM outputgenerateObject() with strict schemasLLM output that doesn't match the schema triggers an automatic retry rather than a runtime crash downstream.
maxRetries: 1On all LLM callsVercel AI SDK handles 429 retry with exponential backoff automatically. One retry covers transient errors without implementing manual retry logic.

Every bug encountered and how it was resolved
ErrorRoot CauseFix Applied
"Planner did not produce a chart execution path"User asked conversational question on Dashboard tab. Planner returned needsData: false, skills: [] but dashboard path required chart skill.Added fallback: when !plan.skills.includes('chart'), route to executeInquiry() instead of throwing.
"Http failure response for /api/analytics: 0 undefined"HTTP status 0 = browser could not reach server at all (connection refused). Server was restarting. Angular's error handler showed raw technical message.Added if (error.status === 0) check in analytics-api.service.ts returning friendly message: "Cannot reach the server."
"Chart planning failed." (silent)Two causes: (1) Zod schema had .max(3) on widgets array — LLM returned 4 → validation fail → old .catch() returned empty widgets. (2) Rate limit error caught silently.Removed .max(MAX_WIDGETS) from Zod schema (slice after). Removed all silent .catch() fallbacks on runChart calls.
"Groq API quota reached. Try again in 19m21s"All 4 LLM roles were set to 70B. Memory extraction (after every response) added ~700 tokens to 70B budget → ~5,200 tokens/request → immediately hit 6,000 TPM.Reverted memory role to 8B (llama-3.1-8b-instant). 8B has its own separate 6,000 TPM pool. 70B budget restored to ~2,600/request.
Stale server logs after restartPowerShell log redirect was reading old log file buffer after restart. Logs showed old model names.Verified actual compiled output in dist/ai/model.js directly. Confirmed via GET /health returning 200.
Chart widget always empty after removing .max()Field validation was still dropping widgets because labelField/valueField names didn't match actual data keys (case mismatch or underscore differences).The auto-detect valueField logic in toWidgetPlan() scans data for the first numeric column if LLM forgot to set one.
